## 1. 一句话结论

这不是 UE 技巧问题，也不是模型写错了蓝图；是**三个系统级缺陷叠加**：

1. **能力边界不可见**——「新建关卡」在规划者能力表（`agent/catalog.py` 的 `CATALOG`）里根本不存在，同时 `create_blueprint` 这种「执行器能跑、规划者看不见」的动作也不在表里；
2. **静默降级**——一段需求拿不到窗口时，代码只写一句 `block_note`（"只记录待办"）就放行，不 fail-fast、不升级人工、不留结构化缺口；
3. **裁决语义混淆**——集成矩阵把「没证据」和「失败」塞进同一个 `ok=false`，而人审门把「0 扇窗口」渲染成**空白**，缺口对领审人是不可见的。

结果：整句 36 秒跑完，**只做了一件事——启动编辑器**；B（新建关卡）、C（实现 FPS 玩法）两段需求整段蒸发，而人审记录写着「通过」。

## 3. 根因分层

### RC-1 规划者能力表 ≠ 执行器能力集（能力边界不可见）

- `create_blueprint` 在 `agent/catalog.py:116`（`DIRECT_ACTIONS`）、`:158`（`EDITOR_LOCK_ACTIONS`）里，`agent/sequence.py:136` 有完整执行分支，但**不在 `CATALOG`**（`:8-100`）。
  → 它由 `_create_and_goal` / `grounding.link_asset` 在代码侧插入，规划者/理解器的提示里从来没有它（`catalog.system_prompt()` 只遍历 `CATALOG`，`:364-394`）。
- `create_level`（新建关卡）**全仓库不存在**：`CATALOG`、`DIRECT_ACTIONS`、`sequence._run_action` 都没有。全仓库对"关卡"的语义只有**当前关卡**（`sequence.py:343-373` 的保存、`:1571`/`:1807` 的存盘、`SceneTools.get_current_level`）。
- 因此「新建一个关卡，名字为 L_NewTest2」这句话在**表示层就无法表达**。规划者的处理是正确的（如实写进 `pending_note`），坏掉的是后面的流程。

判定特征（30 秒认出同类问题）：某个需求动词在 `CATALOG` 里搜不到，但执行器（`sequence._run_action`）或 MCP 工具层（`data/ue_mcp_index.json`）里其实有等价能力。

### RC-2 无法规划 = 静默降级（silent drop）

`agent/brief.py:236-237`：

```python
if not wins and not scope.get("blocked"):
    scope["block_note"] = "没有可执行的窗口，只记录待办，不进执行。"
```

- 只写了文案，**没有** `capability_gap`、没有记候选动作（`catalog.note_candidate`）、没有让人审门拦住、没有让 run 状态变化。
- `agent/brief.py:739-935` 的 `materialize_scopes` 只物化任务书**已声明**的窗口；对 0 窗口范围不做任何补救、不报错（`:785-803` 第一遍遍历 `scope.get("windows") or []`，空就是空）。
- 于是范围 B/C 产出 `window_ids: []`（`run_windows.py` 的记录里 B/C `"window_ids": []`），既没有窗口也没人负责。

### RC-3 人审门只审形态、不审覆盖（缺口被渲染成空白）

- 固化件 `.md` 的表格只有三列 `任务范围 / 尚未完成的全部主要内容 / 估时区间`（`brief.py:447`），**没有窗口列**——`20261024-192830-L_NewTest2-FPS.md` 里完全看不出 B/C 一扇窗口都没有。
- 控制台人审表**只在有窗口时**才画「窗口：」那行（`brief.py:659-662`）：
  ```python
  wins = scope.get("windows") or []
  if wins:
      ... bits.append(f"[dim]窗口：{marks}[/dim]")
  ```
  → 缺口的表现形式是**缺席**，而空白格与「一切正常」在人眼里无法区分。
- 结果：人审 1 通过，覆核的是「估时区间、交付条目、依赖关系」这些形态，而不是「每一段交付是否至少有一扇能跑的窗口」。

### RC-4 集成分不清「没证据」与「失败」，且不归因

`agent/run_windows.py:1045-1053`：

```python
checked = [one for one in matrix if one.get("ok") is not None]
ok = all(one.get("ok") for one in checked) if checked else False
if not checked:
    label = "矩阵没有可验证的项，不算全过"
```

- 口径本身是对的（`ok=None` 是"不适用"，不撑成功；见 `:966-969` 引用的 20261021-195220「五项空转全绿」教训）。
- 缺的是**第三态**：`checked` 为空时应该区分「本次什么都没交付（no_evidence）」与「交付了但没过（judge_failed）」。当前一律 `ok=false` + `stop_reason="judge_failed"`（`.json:331`），summary 里也不点名是哪几段需求没交付。
- 集成 note 也因此只剩「完成 W1；失败 W2」，读者无法从中得知「新建关卡和 FPS 玩法根本没做」。

### RC-5 范围判定算对了，却没传到结论上

- `agent/harness.py:247-275` `scope_marks` 已经写明「没窗口的范围永远不算完成」（`:250` 注释直接引用了 20261021-195220 的 B/D/E 零窗口教训），`:266-267` 给出 `reason="没有可执行的窗口，只记待办"`。
- `agent/harness.py:278-299` `contract_status` 只在 `status == "成功"` 时才用范围判定改判。
- `agent/run_windows.py:1524-1556` 先把状态定成「部分完成」（W1 done + W2 failed 且无下游依赖 ⇒ `:1545-1546`），于是 `:1573` 的 `if adjusted == "部分完成" and status == "成功"` **永不成立**，`open_scopes` 的缺口说明（`:1576-1580`）根本不会写进集成 note。
- 最终状态「部分完成」在语义上把「只做了一件无关紧要的事」和「大部分做完、差一点」混为一谈。

| 既有防护 | 为什么没生效 |

| 规划者"看不准就不要编新动作"（`catalog.py:368`） | 它照做了：如实标注"动作表里没有建关卡的动作"。缺的是**收到这个信号后的处置**。 |

## 5. 本次修复（三轴）

### 5.1 补齐能力：`create_level` 全链路（task-1）

- `CATALOG` / `DIRECT_ACTIONS` / `EDITOR_LOCK_ACTIONS` / `_VERIFY` 增加 `create_level`，槽位 `level`；规划者提示自动带上它。
- `plan_windows`：槽位归一与解析（裸名 `L_NewTest2` → `/Game/Maps/L_NewTest2`），`materialize("create_level", …)` 必须 `realizable=True`。
- `sequence._run_action`：`AssetTools.exists` 判存在（幂等）→ `AssetTools.duplicate`（模板默认 `/Game/Maps/L_NewTest`，可被 `UE_LEVEL_TEMPLATE` 覆盖）→ `AssetTools.save_assets` → `SceneTools.load_level` → `SceneTools.get_current_level` 复查含目标名；任何一步失败都返回具体步骤的 error，不假成功。
- **不依赖模型的补窗**：`plan_windows.scope_windows(scope, query)`——任务书/理解器把「新建关卡 X」写成 0 窗口时，由代码补出窗口。这是本次最关键的一处：它把"模型没想到"从致命变成可恢复。

### 5.2 堵住静默：零窗口不再是终点（task-2）

- `materialize_scopes` 对「未 blocked、无外部依赖、0 窗口」的范围：先调 `scope_windows` 补窗；补不出来 ⇒ 标 `capability_gap`（结构化：原因、交付条目、缺的动作词）+ 记 `catalog.note_candidate` 候选。
- 任务书 md/人审表**显式出现「能力缺口」字样**，不再用"只记录待办"糊过去。
- `harness.scope_marks` 给出结构化 `gap` 字段；有 `capability_gap` 范围时整句状态记**未完成/未交付**，并放开 `run_windows.py:1573` 的 `status == "成功"` 前置条件，让缺口说明无论如何都进集成 note。

### 5.3 裁决三态：`no_evidence` 独立成态（task-2）

- `_run_integrate`：`checked` 为空且存在缺口范围 ⇒ `verdict="no_evidence"`，summary 点名「哪些范围没交付、原因是能力缺口」，`stop_reason="no_evidence"`；`checked` 非空但没过仍记「矩阵未全过」。
- `ok=None` 仍然是"不适用"，不撑成功——**不放宽裁判口径**换成功率。

### 5.4 顺带修掉的同族缺陷（Lead 复核 + task-4 自查发现）

同一次复核里挖出两个**同一族**（静默丢证据 / 声明点无人守）的缺陷，一并修掉——它们都会让"看起来过了"与"实际没有证据"混在一起：

1. **归档证据被二次覆盖**（task-5）：`run_windows.py:1083` 带 `hashes/matrix` 归档后，`:1734` 收尾又调 `_archive_run(state, md_path=path)` 不带这两个参数，`:1199` 的 `hashes or []` / `matrix or []` 把证据清成空。
   实测现场：`data/archive/20261024-192858/deliverables.json` = `{"hashes": [], "matrix": []}`，而同 run 的 `data/runs/…/20261024-192858.json` 里 W2 的矩阵有 5 项。
   修法：`_archive_run` 改合并语义（`None`＝"没给，保住已有"，显式空列表＝"就是要空"），并加 `written_by` 标明写入来源；新增 `eval/check_archive_fidelity.py` 钉住。
2. **`create_level` 的裁判绑定声明漏了一处**（task-6）：`agent/harness.py:20-38` 的 `_KIND_BY_ACTION` 没有 `create_level`，而 `:173 build_criteria` 与 `:126 _window_ids_for` 都靠这张表。
   后果：一个**真的建成了关卡**的 run 可能产不出任何条款 ⇒ 集成矩阵 `checked` 为空 ⇒ 又变成「矩阵没有可验证的项，不算全过」的假失败——本次要根除的缺陷换个入口重现。
   修法：补 `"create_level": "editor_assert"`，并加"条款产出 + 绑定到那一扇 + 认不出的动作仍不产条款"三态断言。
3. **同样的声明缺口还有两处，但补法被证伪了**（task-8）：`create_widget_blueprint` 与 `bind_blueprint` 也缺 `_KIND_BY_ACTION` 映射。补上之后实测发现更糟：这两扇的执行分支（`sequence._create_widget_blueprint`、`bind_slot` 段）**根本不产出 `judge_kind`/`test`**，于是"从没判过"会被写成"判过了且没过"——正是本次要根除的混淆。
   处置：**回滚这两处映射**，改为在 `eval/check_capability_gap.py` 里钉一条**两侧对齐**断言（用 `inspect.getsource` 读 producer 侧有没有声明判词：没声明就不许表里有映射；哪天 producer 声明了，这条会反过来催"映射该补上"）。
   这是本次唯一一处"发现缺口但**故意不补**"的地方，理由是补了比不补更坏——先修证据源，再补声明点。

这三条说明：**"新增一个动作"从来不是一个文件的改动，而是十几处声明点的同步**（catalog 表、DIRECT、EDITOR_LOCK、`_VERIFY`、槽位归一/解析、sequence 分支、producer 侧判词、kind 映射、依赖/补窗路径、离线检查、CI），
其中任何一处漏掉都会静默退化成"证据为空"或"把没判过写成没过"。这正是升级计划里 parity 守卫（P0-1）要自动化掉的东西。

### 5.5 同一族缺陷的镜像面：**真做成也会被记成失败**（task-7）

补 `create_level` 之后，fix-gap 实测出一条更要命的事实：`_run_integrate` 的 5 项子判定（重复请求幂等 / 拒答路径 / 延迟窗口 / 断线重连 / 未知态恢复）全是**运行期鲁棒性行为**——一个只有 `launch_editor` + `create_level`、条款全过的 run，这 5 项仍旧全 `ok=None`，于是 `checked` 为空 ⇒ `ok=False` + 「矩阵没有可验证的项，不算全过」+ `stop_reason=judge_failed` + 整句「部分完成」+ **退出码 1**。

也就是说：**修复让「新建关卡」真的能建成之后，真做成了也会被判失败。** 这是本次要根除的缺陷的镜像面（同一套矩阵语义，两个方向都错），不修掉就不算把需求修通。

修法（task-7）：matrix 补第六项**「交付验收」**，四态互斥——

| 场景 | 交付验收 | 结果 |
| --- | --- | --- |
| 有条款 `passed=False` | `False` | 真失败，看得见 |
| 一条条款都没有 | `None` | 什么都没声称 ⇒ 不适用（保住 20261021-195220 的教训） |
| 条款非空全过、且无缺口范围 | `True` | 「矩阵全部通过」 |
| 条款非空全过、但有缺口范围 | `None` | 有范围没交付 ⇒ 交付验收不适用（缺口由「未完成」+ `no_evidence` 点名） |

第四态刻意选 `None` 而非 `False`：把「没做」和「做坏了」混成一个 `ok=false`，正是本次失败的成因之一；缺口已经由范围判定和 `no_evidence` 各自点名，不需要第三个地方再混一次。

顺带修掉同一次复核发现的**归档 run json 落后一版**（归档发生在 `state.save()` 之前，实测 `archive/<id>/<id>.json` 是 `status=running / integration=None`，而 runs 目录里已是终态）。

### 5.6 独立复验又证伪出三条「假通过」方向的口子（task-9 / task-10）

修复过程本身也验证了这套系统的自检能力：独立复验方用**自己写的**检查去证伪前序修复，又挖出三条同族缺陷，全在集成矩阵的**聚合层与措辞层**，方向都是**假通过**（比假失败更危险）：

| # | 缺陷 | 实测 | 修法 |
| --- | --- | --- | --- |
| T9 | 聚合层只看 `checked`，而「拒答路径」有 paused 扇就给 True、「延迟窗口」窗口有终态就给 True（**失败也算过**） | 有缺口 + 延迟窗口 True ⇒ 集成扇 `ok=True`、「矩阵全部通过」、`stop_reason=ok`，而 run status 是「未完成」；md 里「W3 成功/矩阵全部通过」与「集成 未完成」并存 | 聚合层加**交付否决**：缺口/失败扇/暂停扇任一存在 ⇒ `ok=False` + 点名；缺口时 `verdict=no_evidence` 不再要求 `checked` 为空。五项判据一字未改 |
| T10-A | 矩阵第 5 项写成 `"ok": True if stuck else None`（HEAD 本为 `"ok": not stuck`），语义反转 | W2 卡在 `running` 时该项给 `True`，还占一个 `checked` 名额撑「矩阵全部通过」 | 改为 `"ok": False if stuck else None`；不卡住时仍是 `None`（不适用、不占名额） |
| T10-B | `scope_marks` 里 `elif not window_ids:` 排在 `elif external_dep:` 之前 | 「等外部」的零窗口范围被说成「没有可执行的窗口，只记待办」——正是本轮要根除的话术 | 调换分支顺序；label 不再不加限定地说「矩阵全部通过」，改为「矩阵全部通过；另有范围等待外部：C」。**红线：`waiting_external` 不进 veto** |

T10-A 值得一提：这处反转**不是本次修复引入的**，`git show HEAD` 显示 HEAD 是对的、工作树里早就错了——也就是说它在我接手前就躺在那，只是因为那时"矩阵 checked 为空 ⇒ 反正都是失败"而被掩盖；直到 T7 把「交付验收」补上、矩阵有了 `True` 的可能，这个假通过才变得可观测。**这是"修复一个缺陷会让另一个沉睡缺陷显形"的典型例子。**

## 7. 未覆盖 / 遗留（诚实边界）

1. **`create_level` 的来源是"复制模板"**：`/Game/Maps/L_NewTest` 是工程里唯一的 `.umap`，MCP 工具面（`data/ue_mcp_index.json`，830 工具，生成于 2026-09-21）里没有 `new_level`/`create_map`，`execute_tool_script` 只允许 `re/datetime/copy/time/math/json`，导不进 `unreal`。所以新关卡是"模板复制"而非"空关卡"。要真正的空关卡，得在 UE 插件侧加一个 `SceneTools.new_level`（列入升级计划）。
2. **本次只修"能不能规划/会不会静默/怎么裁决"**，不等于把「简易 FPS 射击玩法」真的实现出来。C 段仍需要模型按窗口逐扇施工（新蓝图、输入、开火、命中、HUD），这属于后续真实 run，不在本次修复的验收口径里。
3. **真机终验已完成**（见 5.8）：经用户授权临时放开写策略，已真建出 `/Game/Maps/L_NewTest2` 并切为当前关卡，幂等与条款绑定均已实测。终验后写权限已收回。
4. **能力表膨胀的治本项未做**：`create_blueprint` 仍靠代码侧插入而不是规划者可见，`CATALOG` 与执行器的一致性**没有自动守卫**。这类"补一个动作修一次"的模式，正是下次升级计划要改成 parity 守卫的地方。
5. **`create_widget_blueprint` / `bind_blueprint` 的声明缺口故意没补**（task-8 回滚）：它们的执行分支不产出 `judge_kind`/`test`，先补映射会把"从没判过"变成"判过了且没过"。已用 `eval/check_capability_gap.py` 的 `check_binding_parity()` 钉成**两侧对齐守卫**（producer 没声明判词 ⇒ 不许有映射；声明了 ⇒ 必须补），真正的修法是先在 `sequence` 侧让这两扇像 `_create_level` 那样返回判词，再一起补映射——列入升级计划 P0-1 的任务单。
6. **`agent/supervise.py` 的句子级补窗只覆盖本次涉及的动词**（新建关卡/新建蓝图），更广的"需求动词→动作"映射（加输入、开火、计分、HUD）仍会落到缺口路径——由 `capability_gap` 兜住并点名，但不会自动实现。
7. **老 run 记录续跑时状态词仍是「部分完成」**：`scope_marks`/`contract_status` 只认显式 `capability_gap` 字段（刻意不按"窗口为空"反推，否则 `eval/check_harness.py:731-737` 的人工拼零窗口用例会红），所以 192858 这类老记录 `--resume` 时整句仍是「部分完成」；但集成扇照认结构性零窗口，仍会记 `no_evidence` 并点名。这是有意识的兼容取舍，不是遗漏。
