## 1. 一句话结论

这条需求是**一个纯 UMG（控件图）改动**：在已存在的 `WBP_FpsHUD` 左下角血条左侧 10 像素处加一个
头像框、框内加可配置图片控件。理解器其实**已经正确给出** `edit_widget_blueprint`（事件
`intent.actions == ["launch_editor","edit_widget_blueprint"]`），但工作流有两处真缺陷，把它变成
「一处假成功 + 一处假失败」：

1. **路由缺陷**：`_clause_accounted` 认不出「添加一个头像框」「里面可以配置图片」这两个半句，
   `_covers_after_gate` 判「没盖住」⇒ 整句被**丢弃**、改走 `solve`（`source=solver-fallback`）。
   `solve` 的收口固定是 automation 过滤器，UMG 改控件产不出过滤器 ⇒ W2 必然诚实失败（`judge_failed`）。
2. **假成功缺陷**：stitch 补回的 S1 `edit_widget_blueprint` 被 `build_fps_hud` 当成「FPS HUD 请求」
   （「血条」+ 资产名 `WBP_FpsHUD` 里的 HUD 字面量凑够两票；或交付条目「不遮挡 txt_RocketAmmo」里的
   控件名），于是拿**合同控件「新增 无，原本就在；图形血条已就位」报成功**——头像框一个字都没加，
   却记成成功。

净效果：头像框没做出来，却有窗口记成功（W1、S1），另有窗口记失败（W2、W3），整句停在
`judge_failed` 的「部分完成」。**这不是 UE 技巧问题，也不是模型能力问题，是工作流把一条能规划成
控件图的需求判成「没人接」又拿错合同冒充完成。**

## 3. 根因

### RC-1（真缺陷，已修）控件元素半句不被 `_clause_accounted` 认领 ⇒ 整句掉进受控求解

`agent/plan_windows.py:_clause_accounted` 逐半句判断「有没有被已拆出的动作接住」。它已有 HUD 半句
（`_HUD_CLAUSE_RE`）、改码、场景移动、放灯（`place_light`）等分支，但**没有控件图动作的分支**。
于是「添加一个头像框」「里面可以配置图片」两条被判 `uncovered` ⇒ `_covers_after_gate` 返回 False ⇒
`plan_windows` 在「求解开着」时调用 `_solve_fallback_windows` 把整句换成一扇 `solve`。

`solve` 扇的收口判据固定只取 automation 过滤器（`solver.py` §5），UMG 改控件根本没有对应
automation 测试 ⇒ `no_criteria` ⇒ 「不编证据」诚实失败。这是**路由层把可做的需求扔进做不了也验不了
的通道**，与 20261024 复盘里的「能力边界不可见 + 静默降级」同一类。

### RC-2（真缺陷，已修）`is_fps_hud_request` / `build_fps_hud` 拿 FPS HUD 合同冒充非 HUD 控件

`agent/fps_hud.py:is_fps_hud_request` 的判据是「命中任一 `_HUD_TOKENS`」+「控件名直接命中 或
读数词≥2 类」。这句里：
- `_HUD_TOKENS` 带 `"HUD"`，而资产名 `WBP_FpsHUD` 天然含 `HUD` ⇒ 与「血条」凑够 2 票；
- 交付条目「不遮挡 `txt_RocketAmmo` 等现有元素」是**约束**，却命中了合同控件名。

两者任一都把「加头像框」误判成「摆 FPS HUD 读数」。`build_fps_hud` 随后只核对合同控件
（txt_Health 等「原本就在」），编译保存后报成功——**需求根本不是合同里的东西，却被合同判词冒充完成**。
这是「假成功」，比失败更危险。`run_windows._run_window` 的「控件图扇必须有写工具」守卫也没拦住，
因为 `build_fps_hud` 的 `tools` 里确有 `set_slot_property/set_text/CompileWidgetBlueprint` 等写调用
——它确实写了，只是写的不是用户要的头像框。

### RC-3（潜伏风险，本次不改）`solve` 的 `_pick_criteria` 只验「过滤器存在」，不验「相关性」

W1 之所以能记成功，是 `solver._pick_criteria` 让模型从真清单里挑了一个 `AIAgent.Fps.Hit`，
而 `_filter_in_list` 只校验「这个名字在清单里」，不校验「它与这次改动相关」。于是与改动无关的
automation 也能给 UMG 任务收口。RC-1 修好后这条路径对 UMG 不再触发，但作为通用假成功风险记录在案
（见 §6）。

## 4. 本次修复（不新增动作表、不加关键词表）

修法原则：**规则层接不住时，以（已经问过的）大模型为准，而不是在代码里继续堆词表/动作表。** 具体三层：

1. `agent/plan_windows.py`（路由）
   - 不再给 `_clause_accounted` 加「头像框/图片」关键词。改为在 `_covers_after_gate` 判「没盖住」时区分两种：
     理解器**`unresolved` 为空**（模型认为它盖住了整句）、且给的是**可实现窗口** → **以理解器（大模型）
     的窗口为准**，照常返回 `source=understood`，不因纯词典没认出就掉进 `solve`；
     `unresolved` 非空（模型自认有缺口）或窗口不可实现 → 仍退求解扇 / 缺口（不误伤、不静默丢）。
   - 这里**不额外再多问一次模型**：理解器本来就是大模型、已经问过；问题只在于纯规则 `_clauses_accounted`
     事后用词典去否决它。修的是「不许纯规则否决已问过的大模型」，不是「再多问一遍」。
   - 效果：头像框需求不再因纯词典缺口掉进 `solve`；`plan_windows(原句)` 由
     `solver-fallback/solve` 变 `understood / [launch_editor, edit_widget_blueprint]`。
2. `agent/fps_hud.py`（判词）
   - `is_fps_hud_request` 遇合同外控件（头像框 / 头像 / 图片 / 贴图 / Image…）直接 `False`。
     `hud_windows` / `build_fps_hud` 都经它，故不再拿 HUD 合同冒充；真 HUD（单读数 / 整句七控件）一字不动。
3. `eval/check_widget_route.py`（新增，已进 `.github/workflows/offline.yml`）五条断言：
   - 规则词典**认不出**「头像框」半句（`_clause_accounted(...) is False`）——证明没用关键词表硬覆盖；
   - 整句**不掉进 solve**：保留理解器给的 `launch_editor→edit_widget_blueprint`（`source=understood`、
     `planner_called=False`），且理解器**只被问一次**（不额外多问）；
   - `is_fps_hud_request(头像框)` 为 `False`、`hud_windows` 为 `None`；真 HUD（单读数 + 整句）仍 `hud-rules`；
   - 动作表里没有「头像 / 图片」类新动作（未新增动作）。

修法边界：不替模型编窗口（窗口来自理解器）、不改动作表、不碰合同控件名。

## 7. 续修（本轮）：把 UMG Spec 内核接进执行，让系统真能把头像框建出来

§6.1 说的「模型产 Spec」这一步本轮已接上（不是再修 bug，是接通已有内核）：

- `agent/spec_pipeline.py::produce_spec`：通用「模型产 Spec」入口——按域 `SPEC_HINT` 让模型输出
  Spec JSON → 解析 → 注入缺省目标 → 域 `validate_spec` 验收；产不出/非 JSON/校验不过一律返回
  `None`（诚实回退，绝不半个 Spec 冒充完成）。没有模型 key 时 `complete_logged` 立即返回错误，
  `produce_spec` 即刻 `None`，离线/CI 行为与接入前一致。
- `agent/umg_spec.py::produce`：UMG 包装——从槽位/句子归地目标 WBP，作为缺省 `widget_blueprint`，
  调 `produce_spec`。执行/复核/回灌仍在内核 `build()` 里。
- `agent/run_windows.py::_maybe_attach_umg_spec`：包在 `_run_window` 的 monolith 控件图扇执行前，
  只对**非 FPS HUD** 的 `edit_widget_blueprint` 扇产 Spec 挂到窗口（FPS HUD 链带
  `hud_controls`/`hud_op`，交给 `build_fps_hud` 固定合同，不在此产通用 Spec；UMG 开关关着 / 模型
  产不出也原样交回）。挂上后 `sequence.repair_blueprint` 走已有的 `build_umg_spec`：确定性建
  `Border/Image/…` 节点 + 只读复核（控件在不在 / 类对不对 + 编译）。
- `eval/check_umg_spec_produce.py`（新增，已进 `offline.yml`）：钉「合法 Spec 解析校验 / 坏 Spec 被拒 /
  产出的 Spec 能真建出来并复核 / attach 只对非 HUD 控件扇接线」四条，全离线（模型替身 + 假 call）。

于是「给血条左边加头像框、里面配图」这类需求的完整链路变成：
理解器 → `edit_widget_blueprint` → 模型产 UMG Spec（`Border` 头像框 + `Image` 图片，锚点/坐标/尺寸落地）
→ 内核确定性执行 → 只读复核 + 编译 → 交付。**系统自己把控件树建出来并验证，不再假成功、也不再做不出。**

残余（诚实边界）：Spec 内核能建节点、设通用属性、设锚点/槽位/画刷；「把图片源暴露成设计器里可直接
配置的公开参数（`ToggleWidgetAsVariable` 之类）」这类**变量暴露/绑定**语义不在当前 kernel 的抽象原语里，
需要时另加一条原语与断言。头像框与图片控件本身、位置与不遮挡属于本 kernel 已覆盖范围。

## 8. 为什么不是「新增动作表」，以及「接不住为什么必须问大模型」

（回应复核意见，记录口径，防止下次又走偏）

- **没有新增动作表**：`agent/catalog.py` / `agent/actions.py` 本次**零改动**，`check_catalog_parity` 仍是
  「执行器 32 扇、规划者 24 扇、白名单 10 条」。也没有任何「头像框 / 图片」类新动作。头像框依旧由
  既有的 `edit_widget_blueprint` + UMG Spec 内核完成。
- **也没有新增关键词表（已自我纠正）**：最初一版我给 `_clause_accounted` 加过 `_WIDGET_ELEMENT_RE`
  （认「头像框/图片/控件…」）。这正是「加词表」的老毛病，已**删除**。现在规则词典对「加一个头像框」
  仍返回「认不出」（`check_widget_route` 专门钉住这一点），改由下面的机制处理。
- **「接不住为什么没问大模型」——其实先问了，是规则把它否了**：本 run 里理解器（大模型）**先**被调用，
  且正确给出 `edit_widget_blueprint`（事件 `intent.actions`）。真正的问题是**纯规则的 `_covers_after_gate`
  用一个词表把大模型的答案否掉**，塞进 `solve`（automation 收口，UMG 必然验不过）。所以根因不是
  「没问大模型」，而是「问了，却被规则否决」。本次修法就是把这条否决去掉——
  **模型 `unresolved` 空、窗口可实现时，以已问过的大模型为准，纯规则不再否决**（不再额外多问一遍）。
- **分工口径**：动作表只收「有执行器 + 有裁判」的能力；词表只做确定性快路；**两者接不住时以已问过的大模型
  为准（unresolved 空）或进缺口/求解（unresolved 非空），不靠扩动作表/扩词表**。本条与 §4、§7 一起构成
  20261118-152628 的完整修法。
- **为什么不是「无脑信理解器」**：`unresolved` 非空（模型自认有缺口）或窗口不可实现时，仍进缺口 / 求解扇，
  避免 20261024 那种「半句蒸发」；只在 `unresolved` 空、窗口可实现时才保留理解器的窗口——既不静默丢需求，
  也不让纯词表否决大模型。
